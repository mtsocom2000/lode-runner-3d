## 一、概念（v2.0）

### 1.1 一句话

**一张原版 Lode Runner 关卡，沿中线折 90°，贴在墙角的两个竖直面上；两墙之间是水面，水中央的岛台上放着必取宝物——只有从两侧墙上伸出的砖块小道（以及后期的连杆/柱）能到得了它。**

### 1.2 结构定义

```
关卡数据 K：一张 2D 瓦片网格，W 列 × H 行（字符行数组）
            cols 0..C-1  → 墙 A（关卡左半）
            cols C..2C-1 → 墙 B（关卡右半）
            折痕位于 col C-1 与 col C 之间

墙 A：竖直平面 x = -(N-1)/2；col c 沿 z 排列，c=C-1 贴着折痕
墙 B：竖直平面 z = -(N-1)/2；col c 沿 x 排列，c=C   贴着折痕
水面：两墙围起的中部区域（y = waterY），任何角色不可进入
岛台：水中 4×4 / 5×5 的砖块堆叠（≥1 层），台上有必取宝物
小道：1 格宽、若干层的砖块通道，从墙 A / 墙 B 伸向岛台
连杆：后期扩展 —— 岛间、岛↔墙、柱↔柱 的横杆
```

**摊平即原版**：把两面墙沿折痕展开到同一平面，就是一张完整的、平的 2D 关卡。
**相机**：正交、约 45° 轴测、正对墙角棱线，**全程固定**。

### 1.3 为什么这个方向成立（设计论证 · 本作核心结论）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **重力一致，折叠才成立** | 两面都是**竖直面** → 共用同一重力方向（世界 -y）。若把任何一面换成地面，两半的重力就不一致，折叠立刻破裂。这是本作 3D 成立的**前提条件**，不是巧合。 |
| 2 | **可读性被保住** | 玩法面 = 两面各 1 砖厚的浮雕 → 除 1 格纵深外**没有自遮挡** → 保住了原版"一眼看清全局"的公平性。这是 v1.2 山体方案做不到的（那座山越高越糊）。 |
| 3 | **规则零翻译** | "1 砖厚"＝原版的格子模型。挖 / 回填 / 活埋 / 梯 / 杆 / 金 全部按原版语义直接生效，不需要自创规则。v1.2 则必须发明"梯 Δh=2""横杆锚点等高""高度场"一整套。 |
| 4 | **可达性可验** | 水面不可进入 → 可走集合 = 两片薄格栅 + 小道 + 岛台，图极小、极薄 → validator 可靠。v1.2 的 14×14 高度场需要 BFS 兜底且反复出错。 |
| 5 | **3D 是机制，不是布景** | 折痕 + 水沟。水不可通行 ⇒ 两面墙**只能经岛台相连** ⇒ 岛台天然成为隘口/必守点（免费的谜题结构）。 |
| 6 | **忠于原版** | 关卡本体就是原版的一张关卡，而不是"3D 化改造"。 |

### 1.4 明确放弃的设计（防回归清单）

| 放弃项 | 原因 |
|---|---|
| 底面高度场 `h(x,z)`、角心山体/台地/峰群 | 高度即遮挡：越"丰富"越不可读；且把第三维用在布景而非机制 |
| 墙面深度网格 `d∈{1,2,3}` 的"隆起"语义 | 同一病因；且"看着能站却上不去"的可达性陷阱 |
| 梯成对声明 + Δh=2、横杆"两锚点等高且中间有落差" | 原版规则已足够，自创规则是负担 |
| **X-ray 作为必需件** | 新形态下无遮挡问题 → X-ray 从"必做"降级为**不需要** |
| 相机旋转 / 信息不对称支柱 | 两面同时可见 ⇒ 旋转无用途 ⇒ **不做旋转**。原先悬置的"v1 不做旋转"就此**关闭**（不是推迟，是不需要） |
| "外密内疏""三带空间语法""台地丰富度向心递增" | 全部依附于已作废的山体模型 |

### 1.5 新增规则（只需要 3 条）

1. **折痕边**：墙 A 最内列 ↔ 墙 B 最内列、**同一行** → 视为相邻。走过去即跨过折痕（角色朝向需随之转 90°，见 §八-4）。
2. **水面不可走入**：在墙面平面内，"朝水"方向**根本不是合法方向** → 输入直接被判非法并阻止（不是"走过去再淹死"）。
3. **落水（扣 1 命）只有两条途径**：
   - ① **坠落**：走进平台的天然断裂处，下方无砖接住 → 一直落到水面；
   - ② **跳下**：在连杆上按"下"跳下，而落点**不是岛台** → 落水。

> 除此之外，原版的全部规则照旧（见 §四 tiles 语义）。

## 二、可行性判定

| 项 | 判定 | 依据 |
|---|---|---|
| 折面渲染（两面墙承载一张关卡） | **OK** | v9 / v10 mock 已渲染验证 |
| 统一立方体砖 + 带缝格阵 | **OK** | v10 mock（`CUBE=0.86` 全局同规格） |
| 砖块堆叠岛台 + 小道 | **OK** | v10 mock（4×4×2 层，小道同规格，均落到墙 row2 高度） |
| 可见水面 | **OK** | v10 mock（水面＋边线＋流动高光；**待优化**：目前太亮、超出墙角范围） |
| 折痕通行 | **OK（待实现）** | 纯数据的邻接边 + 朝向处理，无技术未知 |
| 原版规则（走/梯/杆/挖/回填/活埋） | **OK** | 本仓库原型已全部实现并跑过 25 项无头回归 |
| 水面落水（坠落 / 跳下） | **OK（待实现）** | 规则仅 2 条，判定目标明确 |
| 可达性校验 | **OK** | 图极小（两面各 W×H + 岛台 + 小道），可穷举 |
| 固定 45° 可读性 | **RISK 低** | 两面各约 45° 收缩（横向 ≈0.7）；需注意折痕两侧"直线变成 V 形"的读数习惯 |
| 折痕处手感（朝向 90° 翻转） | **RISK 中** | 唯一需要专门调的手感点；列入 T-SP1 人工 gate |
| 敌人落水行为 | **未定** | 原版只有"被埋"没有水 → 必须新定（§八-2） |

结论：**无技术未知数**；风险集中在一处手感（折痕朝向）与一处规则空缺（敌人落水）。

## 三、架构（v2.0）

```
core/  (纯 TS，零 DOM/three，vitest 无头直测)
├── types.ts            Vector/Face/Tile/Entity/Event/Intents；SimState 可序列化
├── world/
│   ├── fold.ts         ★折叠映射：关卡 (col,row) ↔ (face,u,y) ↔ 世界坐标；折痕邻接表
│   ├── tiles.ts        瓦片语义与关卡装载：X 可挖砖 / = 硬砖 / . 空 / H 梯 / - 杆 / G 宝物 / E 出口
│   ├── water.ts        ★水面定义、落点判定、落水结算触发
│   ├── island.ts       ★岛台/小道/连杆的支撑面与接入点
│   └── graph.ts        通行图：墙面内相邻 ∪ 梯边 ∪ 杆边 ∪ 折痕边 ∪ 小道/岛台边
├── rules/
│   ├── movement.ts     走 / 爬梯 / 跳下 / 杆状态机（抓·横移·松手·跳下）——沿用原版语义
│   ├── dig.ts          挖砖 → 坑、回填（原版 4s 基准 + 走顶加速）、活埋
│   ├── drown.ts        ★落水判定与结算（坠落 / 跳下 两条途径）
│   └── goals.ts        宝物计数 → 出口通天梯（原版规则）→ 触达过关；3 命 / 重生
├── ai/
│   ├── bfs.ts          通行图路径（可配置边集）
│   ├── drone.ts        墙面内巡逻/追击，落水行为按 §八-2 决议
│   └── stalker.ts      可爬崖 / 跨折痕追击，同上
├── level/
│   ├── schema.ts       见 §四
│   └── validate.ts     §四 的 6 条校验
└── sim.ts              固定 60Hz reducer：(state,intents) → (state',events[])
render/
├── scene.ts / meshSync.ts  统一立方体砖 InstancedMesh（墙砖/岛砖/小道砖同规格）、梯、发光横杆、宝物、出口
├── camera.ts               固定正交 45° 轴测
├── water.ts                水面材质 + 边线 + 流动高光（视觉待优化：压暗、收进墙角）
└── fx.ts                   实体 tween、拾取脉冲、落水涟漪、死亡反馈
input/   键盘 → 意图；屏幕向量 → 世界轴（粘滞）；折痕处朝向翻转
app/     主循环、状态机、HUD（宝物 n/m、命数、出口状态）、关卡切换
test/    core 全量 vitest；渲染像素探针脚本
```

红线（继承原型教训）：core 零 three/DOM；sim 确定性可回放；渲染只读 state+events；**改移动函数必须同时跑 AI 回归**。

## 四、关卡格式 v2.0 与校验规则

```ts
{
  id: "L1", name: "折角",
  cols: 14, rows: 10,          // 折叠前的一整张关卡尺寸
  fold: 7,                     // cols 0..6 = 墙 A，cols 7..13 = 墙 B，折痕在 6|7 之间
  tiles: [                     // rows 条字符串，每条 cols 个字符；索引 0 = 最底行
    "XXXX.XXXXXXXXX",          // X = 可挖砖   = = 硬砖   . = 空
    "..............",          // H = 梯       - = 横杆   G = 宝物   E = 出口
    "XXXX.XXXX.XXXX",
    ".....H........",
    "XXXXXXXXXXXXXX",
    "....H.....H...",
    "XXXXXXX.XXXXXX",
    "......--......",          // 横杆穿过折痕：col6 与 col7 各一段，在棱线处相接
    "XXX.XXXXXXX.XX",
    "....G...EE..G."],
  islands: [ { cells:[[5,5],[8,8]], layers:2, treasure:[[6,6]] } ],
  jetties: [ { face:'A', col:0,  row:2, to:0 },
             { face:'B', col:13, row:2, to:0 } ],
  bars:    [ { from:{face:'A',col:6,row:7}, to:{face:'B',col:7,row:7} } ],   // 跨折痕横杆
  waterY: 0.6,
  spawn:   { face:'A', col:1, row:1 },
  enemies: [ { kind:'drone',  face:'A', col:4, row:3 },
             { kind:'stalker',face:'B', col:9, row:6 } ]
}
```

**validator 硬规则（v2.0，共 7 条）**

| # | 规则 |
|---|---|
| ① | 所有格字符合法、行列数一致；砖/梯/杆/宝物/出口均落在网格内 |
| ② | **出口**：宝物未集齐前不可达；集齐后可达（双断言） |
| ③ | 每个岛台至少被 1 条小道或连杆接入；岛上宝物可达 |
| ④ | 每条小道/连杆的两端都落在合法支撑上（墙上的砖格 或 岛台格） |
| ⑤ | 折痕两侧**至少 2 处同行连通**（保证折叠真的被用到，而不是两面各玩各的） |
| ⑥ | 不存在"非落水不可通过"的必经格（任何必经之路都不得强制角色落水） |
| ⑦ | **连杆锚点**：连杆两端必须锚在砖块上，且**连杆所在行 = 支撑砖面之上一层** —— 玩家站在砖面上即可直接手拉横移，**不需要先下降一格**；同时连杆正下方不得为实心砖（否则无法悬挂） |

## 五、技术栈与架构决策

**构建/运行**：Vite + TypeScript(strict) + Three.js(npm ESM) + vitest + eslint/prettier。
scripts：`dev`（本地开发服务器）/ `test`（vitest）/ `build`（→ `dist/` 纯静态）/ `shot`（headless 截图探针）/ `pack`（single-file → 单个 HTML）。

### 5.1 UI 层：原生 DOM，**不引入 React**（v1 决定）

| 考虑 | 结论 |
|---|---|
| 游戏主体 | canvas + 固定 60Hz 循环 → **命令式**驱动。React 的"状态变→重渲染"模型与之冲突：把每帧变化的 sim state 交给 React state，会触发整棵组件树 reconcile，是明确的**反模式** |
| HUD 规模 | 宝物 n/m、命数、出口状态、暂停菜单 ≈ 20 行手写 DOM 更新；为此引入 React+ReactDOM（≈45KB gz 运行时）是纯负重 |
| 最大风险 | 引入 React 就多出"React state vs sim state"两套状态模型要同步。本仓库历次 bug（白块、梯面朝向硬编码、BFS 118/196）**全部**属于"两套数据不一致"——不应再加一层 |
| 测试 | 真正的护城河是 `core/` 纯 TS + vitest 无头回归；React 对 `core/` 零贡献（它只覆盖 DOM 层） |
| 迁移位 | `app/` 层保持独立、无框架依赖。将来若 UI 复杂度超过手写 DOM 的舒适区（关卡编辑器 / 设置页 / 关卡选择 / i18n），迁移成本 = 新增 `ui/` 层，**可逆** |

> 判断依据：**上不上 React 取决于 UI 复杂度，不取决于"这是个游戏"。** v1 的 UI 复杂度 = 3 个数字 + 1 个菜单。

### 5.2 打包与分发：**不要求"部署"**

- `npm run build` 的 `dist/` 是**纯静态文件**（HTML/JS/CSS），不需要服务器、数据库或 Node 运行时；放到任意静态托管（GitHub Pages / Vercel）或 `npx serve dist` 都行。本质是"把一个文件夹放出去"。
- **但直接双击 `dist/index.html` 通常打不开**：打包默认输出 ES Module（`<script type="module">`，`file://` 下受 CORS 限制）且资源为绝对路径 `/assets/...`。这是 **ESM + 打包**的性质，**与 React 无关**（不用 React 也一样）。
- **解法（T0 落地）**：用 `vite-plugin-singlefile` 把 JS/CSS 内联进单个 HTML → `npm run pack` 产出 `dist-single/index.html`，**双击即玩、可直接发给他人**（与当前 mock 的使用方式一致）；开发时仍享受模块化 / 类型检查 / HMR。

## 六、性能（相比 v1.2 大幅下降）

- 实例数：墙砖 ≤ 2 × (C×H) ≈ 280 + 岛台/小道 ≈ 100 → **< 500 个立方体**（v1.2 是 1.2k+）
- 通行图：两面各 C×H ≈ 140 + 岛台/小道 ≈ 20 → **< 200 节点**（v1.2 是 1.3k）
- 结论：性能不再是约束项，可以把预算全部投到**视觉清晰度**（描边/明度分层/落水涟漪）。

## 七、v1 范围

**做**：折面关卡渲染与折痕通行、原版规则全量（走/梯/杆/挖/回填/活埋）、水面与两条落水途径、1~2 座岛台 + 小道（+ 跨折痕连杆）、宝物 → 出口通天梯 → 过关、3 命、无人机 + 攀爬者、L1/L2/L3、core 无头测试全量。UI 用原生 DOM（§5.1）。

## 附录 A：创意源头（已并入 · 原文与旧原型归档于 `legacy/`）

> 来源：原《立方角隙：Lode Runner 3D 游戏创意与关卡企划案》v1.0 + 旧原型 README v0.5。
> 这里只收录**与 v2.0 概念无关、仍然成立**的部分；原案中已被取代的内容见 A.7。

### A.1 一句话定位（未变）

把《淘金者》(1983) 的"挖地困敌、收集逃生、高低差走位"从 2D 升维到 3D，**保留严丝合缝的格子策略判定**。
核心追问始终是：**哪些谜题只有 3D 里才存在？**

### A.2 前人为什么失败（本作要避开的坑）

| 作品 | 做法 | 遗留问题 | 本作对策 |
|---|---|---|---|
| Lode Runner 3-D (N64, 1999) | 关卡 3D 化，角色沿轨道走 | **镜头遮挡**被广泛批评 | 固定正交视角正对墙角 + 两面都是 1 砖厚浮雕 → 无自遮挡（§1.3-2） |

| 本作 | 原版关卡沿中线折 90° | — | 3D 不是视角噱头，而是**机制**（折痕 + 水沟） |

### A.3 仍然有效的设计支柱

1. **固定 45° 轴测、正对墙角棱线**（原案已有；现在是唯一视角，不是可选项）
2. **跨面无缝移动**：进入另一面时输入方向按本地坐标系重映射 —— 即 v2.0 的**折痕边**规则（§1.5-1）
3. **体素挖地**：可破坏 → 凹坑 → 延时自动重组 —— 即**原版挖/回填/活埋**语义（无需自创规则）
4. **规则忠实原版**：无跳跃、守卫也会用杆、杆下/梯井不可挖（护绳）、挖→坠→被埋→以身填坑
5. **逻辑与渲染解耦**：状态是纯 tile 数据，函数不碰 Three.js → 可无头测试（这正是原型跑出 25 项回归的原因，v2.0 继承为 §三 红线）

### A.5 关卡难度递进骨架（保留；关卡内容按 v2.0 重写）
