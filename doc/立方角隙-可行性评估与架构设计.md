## 一、概念（v2.0）

### 1.1 一句话

**一张原版 Lode Runner 关卡，沿中线折 90°，贴在墙角的两个竖直面上；两墙之间是水面，水中央的岛台上放着必取宝物——只有从两侧墙上伸出的砖块小道（以及后期的连杆/柱）能到得了它。**

### 1.2 结构定义

```
关卡数据 K：一张 2D 瓦片网格，W 列 × H 行（字符行数组）
            cols 0..C-1  → 墙 A（关卡左半）
            cols C..2C-1 → 墙 B（关卡右半）
            折痕位于 col C-1 与 col C 之间

墙 A：竖直平面 x = -(N-1)/2；col c 沿 z 排列，c=C-1 贴着折痕
墙 B：竖直平面 z = -(N-1)/2；col c 沿 x 排列，c=C   贴着折痕
水面：两墙围起的中部区域（y = waterY），任何角色不可进入
岛台：水中 4×4 / 5×5 的砖块堆叠（≥1 层），台上有必取宝物
小道：1 格宽、若干层的砖块通道，从墙 A / 墙 B 伸向岛台
连杆：后期扩展 —— 岛间、岛↔墙、柱↔柱 的横杆
```

**摊平即原版**：把两面墙沿折痕展开到同一平面，就是一张完整的、平的 2D 关卡。
**相机**：正交、约 45° 轴测、正对墙角棱线，**全程固定**。

### 1.3 为什么这个方向成立（设计论证 · 本作核心结论）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **重力一致，折叠才成立** | 两面都是**竖直面** → 共用同一重力方向（世界 -y）。若把任何一面换成地面，两半的重力就不一致，折叠立刻破裂。这是本作 3D 成立的**前提条件**，不是巧合。 |
| 2 | **可读性被保住** | 玩法面 = 两面各 1 砖厚的浮雕 → 除 1 格纵深外**没有自遮挡** → 保住了原版"一眼看清全局"的公平性。这是 v1.2 山体方案做不到的（那座山越高越糊）。 |
| 3 | **规则零翻译** | "1 砖厚"＝原版的格子模型。挖 / 回填 / 活埋 / 梯 / 杆 / 金 全部按原版语义直接生效，不需要自创规则。v1.2 则必须发明"梯 Δh=2""横杆锚点等高""高度场"一整套。 |
| 4 | **可达性可验** | 水面不可进入 → 可走集合 = 两片薄格栅 + 小道 + 岛台，图极小、极薄 → validator 可靠。v1.2 的 14×14 高度场需要 BFS 兜底且反复出错。 |
| 5 | **3D 是机制，不是布景** | 折痕 + 水沟。水不可通行 ⇒ 两面墙**只能经岛台相连** ⇒ 岛台天然成为隘口/必守点（免费的谜题结构）。 |
| 6 | **忠于原版** | 关卡本体就是原版的一张关卡，而不是"3D 化改造"。 |

### 1.4 明确放弃的设计（防回归清单）

| 放弃项 | 原因 |
|---|---|
| 底面高度场 `h(x,z)`、角心山体/台地/峰群 | 高度即遮挡：越"丰富"越不可读；且把第三维用在布景而非机制 |
| 墙面深度网格 `d∈{1,2,3}` 的"隆起"语义 | 同一病因；且"看着能站却上不去"的可达性陷阱 |
| 梯成对声明 + Δh=2、横杆"两锚点等高且中间有落差" | 原版规则已足够，自创规则是负担 |
| **X-ray 作为必需件** | 新形态下无遮挡问题 → X-ray 从"必做"降级为**不需要** |
| 相机旋转 / 信息不对称支柱 | 两面同时可见 ⇒ 旋转无用途 ⇒ **不做旋转**。原先悬置的"v1 不做旋转"就此**关闭**（不是推迟，是不需要） |
| "外密内疏""三带空间语法""台地丰富度向心递增" | 全部依附于已作废的山体模型 |

### 1.5 新增规则（只需要 3 条）

1. **折痕边**：墙 A 最内列 ↔ 墙 B 最内列、**同一行** → 视为相邻。走过去即跨过折痕（角色朝向需随之转 90°，见 §八-4）。
2. **水面不可走入**：在墙面平面内，"朝水"方向**根本不是合法方向** → 输入直接被判非法并阻止（不是"走过去再淹死"）。
3. **落水（扣 1 命）只有两条途径**：
   - ① **坠落**：走进平台的天然断裂处，下方无砖接住 → 一直落到水面；
   - ② **跳下**：在连杆上按"下"跳下，而落点**不是岛台** → 落水。

> 除此之外，原版的全部规则照旧（见 §四 tiles 语义）。

## 三、架构（v2.0）

```
core/  (纯 TS，零 DOM/three，vitest 无头直测)
├── types.ts            Vector/Face/Tile/Entity/Event/Intents；SimState 可序列化
├── world/
│   ├── fold.ts         ★折叠映射：关卡 (col,row) ↔ (face,u,y) ↔ 世界坐标；折痕邻接表
│   ├── tiles.ts        瓦片语义与关卡装载：X 可挖砖 / = 硬砖 / . 空 / H 梯 / - 杆 / G 宝物 / E 出口
│   ├── water.ts        ★水面定义、落点判定、落水结算触发
│   ├── island.ts       ★岛台/小道/连杆的支撑面与接入点
│   └── graph.ts        通行图：墙面内相邻 ∪ 梯边 ∪ 杆边 ∪ 折痕边 ∪ 小道/岛台边
├── rules/
│   ├── movement.ts     走 / 爬梯 / 跳下 / 杆状态机（抓·横移·松手·跳下）——沿用原版语义
│   ├── dig.ts          挖砖 → 坑、回填（原版 4s 基准 + 走顶加速）、活埋
│   ├── drown.ts        ★落水判定与结算（坠落 / 跳下 两条途径）
│   └── goals.ts        宝物计数 → 出口通天梯（原版规则）→ 触达过关；3 命 / 重生
├── ai/
│   ├── bfs.ts          通行图路径（可配置边集）
│   ├── drone.ts        墙面内巡逻/追击，落水行为按 §八-2 决议
│   └── stalker.ts      可爬崖 / 跨折痕追击，同上
├── level/
│   ├── schema.ts       见 §四
│   └── validate.ts     §四 的 6 条校验
└── sim.ts              固定 60Hz reducer：(state,intents) → (state',events[])
render/
├── scene.ts / meshSync.ts  统一立方体砖 InstancedMesh（墙砖/岛砖/小道砖同规格）、梯、发光横杆、宝物、出口
├── camera.ts               固定正交 45° 轴测
├── water.ts                水面材质 + 边线 + 流动高光（视觉待优化：压暗、收进墙角）
└── fx.ts                   实体 tween、拾取脉冲、落水涟漪、死亡反馈
input/   键盘 → 意图；屏幕向量 → 世界轴（粘滞）；折痕处朝向翻转
app/     主循环、状态机、HUD（宝物 n/m、命数、出口状态）、关卡切换
test/    core 全量 vitest；渲染像素探针脚本
```

红线（继承原型教训）：core 零 three/DOM；sim 确定性可回放；渲染只读 state+events；**改移动函数必须同时跑 AI 回归**。

## 四、关卡格式 v2.0 与校验规则

```ts
{
  id: "L1", name: "折角",
  cols: 14, rows: 10,          // 折叠前的一整张关卡尺寸
  fold: 7,                     // cols 0..6 = 墙 A，cols 7..13 = 墙 B，折痕在 6|7 之间
  tiles: [                     // rows 条字符串，每条 cols 个字符；索引 0 = 最底行
    "XXXX.XXXXXXXXX",          // X = 可挖砖   = = 硬砖   . = 空
    "..............",          // H = 梯       - = 横杆   G = 宝物   E = 出口
    "XXXX.XXXX.XXXX",
    ".....H........",
    "XXXXXXXXXXXXXX",
    "....H.....H...",
    "XXXXXXX.XXXXXX",
    "......--......",          // 横杆穿过折痕：col6 与 col7 各一段，在棱线处相接
    "XXX.XXXXXXX.XX",
    "....G...EE..G."],
  islands: [ { cells:[[5,5],[8,8]], layers:2, treasure:[[6,6]] } ],
  jetties: [ { face:'A', col:0,  row:2, to:0 },
             { face:'B', col:13, row:2, to:0 } ],
  bars:    [ { from:{face:'A',col:6,row:7}, to:{face:'B',col:7,row:7} } ],   // 跨折痕横杆
  waterY: 0.6,
  spawn:   { face:'A', col:1, row:1 },
  enemies: [ { kind:'drone',  face:'A', col:4, row:3 },
             { kind:'stalker',face:'B', col:9, row:6 } ]
}
```

**validator 硬规则（v2.0，共 7 条）**

| # | 规则 |
|---|---|
| ① | 所有格字符合法、行列数一致；砖/梯/杆/宝物/出口均落在网格内 |
| ② | **出口**：宝物未集齐前不可达；集齐后可达（双断言） |
| ③ | 每个岛台至少被 1 条小道或连杆接入；岛上宝物可达 |
| ④ | 每条小道/连杆的两端都落在合法支撑上（墙上的砖格 或 岛台格） |
| ⑤ | 折痕两侧**至少 2 处同行连通**（保证折叠真的被用到，而不是两面各玩各的） |
| ⑥ | 不存在"非落水不可通过"的必经格（任何必经之路都不得强制角色落水） |
| ⑦ | **连杆锚点**：连杆两端必须锚在砖块上，且**连杆所在行 = 支撑砖面之上一层** —— 玩家站在砖面上即可直接手拉横移，**不需要先下降一格**；同时连杆正下方不得为实心砖（否则无法悬挂） |

## 五、技术栈与架构决策

**构建/运行**：Vite + TypeScript(strict) + Three.js(npm ESM) + vitest + eslint/prettier。
scripts：`dev`（本地开发服务器）/ `test`（vitest）/ `build`（→ `dist/` 纯静态）/ `shot`（headless 截图探针）/ `pack`（single-file → 单个 HTML）。

### 5.1 UI 层：原生 DOM，**不引入 React**（v1 决定）

| 考虑 | 结论 |
|---|---|
| 游戏主体 | canvas + 固定 60Hz 循环 → **命令式**驱动。React 的"状态变→重渲染"模型与之冲突：把每帧变化的 sim state 交给 React state，会触发整棵组件树 reconcile，是明确的**反模式** |
| HUD 规模 | 宝物 n/m、命数、出口状态、暂停菜单 ≈ 20 行手写 DOM 更新；为此引入 React+ReactDOM（≈45KB gz 运行时）是纯负重 |
| 最大风险 | 引入 React 就多出"React state vs sim state"两套状态模型要同步。本仓库历次 bug（白块、梯面朝向硬编码、BFS 118/196）**全部**属于"两套数据不一致"——不应再加一层 |
| 测试 | 真正的护城河是 `core/` 纯 TS + vitest 无头回归；React 对 `core/` 零贡献（它只覆盖 DOM 层） |
| 迁移位 | `app/` 层保持独立、无框架依赖。将来若 UI 复杂度超过手写 DOM 的舒适区（关卡编辑器 / 设置页 / 关卡选择 / i18n），迁移成本 = 新增 `ui/` 层，**可逆** |

> 判断依据：**上不上 React 取决于 UI 复杂度，不取决于"这是个游戏"。** v1 的 UI 复杂度 = 3 个数字 + 1 个菜单。

### 5.2 打包与分发：**不要求"部署"**

- `npm run build` 的 `dist/` 是**纯静态文件**（HTML/JS/CSS），不需要服务器、数据库或 Node 运行时；放到任意静态托管（GitHub Pages / Vercel）或 `npx serve dist` 都行。本质是"把一个文件夹放出去"。
- **但直接双击 `dist/index.html` 通常打不开**：打包默认输出 ES Module（`<script type="module">`，`file://` 下受 CORS 限制）且资源为绝对路径 `/assets/...`。这是 **ESM + 打包**的性质，**与 React 无关**（不用 React 也一样）。
- **解法（T0 落地）**：用 `vite-plugin-singlefile` 把 JS/CSS 内联进单个 HTML → `npm run pack` 产出 `dist-single/index.html`，**双击即玩、可直接发给他人**（与当前 mock 的使用方式一致）；开发时仍享受模块化 / 类型检查 / HMR。

## 六、性能（相比 v1.2 大幅下降）

- 实例数：墙砖 ≤ 2 × (C×H) ≈ 280 + 岛台/小道 ≈ 100 → **< 500 个立方体**（v1.2 是 1.2k+）
- 通行图：两面各 C×H ≈ 140 + 岛台/小道 ≈ 20 → **< 200 节点**（v1.2 是 1.3k）
- 结论：性能不再是约束项，可以把预算全部投到**视觉清晰度**（描边/明度分层/落水涟漪）。

### 八-3 试玩裁定（2026-09-19）：**挖坑反制 —— 守卫必须走进坑里**

用户试玩原话：*"玩家角色在面前挖了一个坑之后，机器人似乎检测到了这个坑，就不会沿着会掉进坑里的路线移动了，这样的话挖坑就失去了意义。"*

这是真 bug，根因是**判据用错了地方**：追击拿**当前地形**建图，坑那一格不是节点 → `findPath` 精确地绕开它。
**裁定**：追击**规划**时按"**地形还完整**"走（把正在回填的坑当成还是砖）；脚下踩空与否仍由 `step` 说了算 ——
也就是原版守卫的行为："不躲洞、照记忆里的地形走、掉进去"。这也是"落坑受困 → 回填 → 活埋"唯一的**入口**。
巡逻段**不变**（仍然躲洞：它是"溜达"，不是"冲着你去"）。

### 八-4 试玩裁定（2026-09-19）：**坑是一格深的"口袋"，不是通往下一层的竖井**

用户试玩原话：*"机器人会从掉入坑中，然后直接掉落在下层地板上。看上去机器人落坑的逻辑延用了玩家角色的逻辑，这是不对的。"*

真 bug。多层楼的几何里，坑曾经只是 `'empty'` —— 于是 `supportOf` 只看"正下方实心"，坑就成了一条
**穿到下一层的竖井**（顺带让"落坑受困 → 活埋"整条链没有入口，玩家也永远不可能被埋）。

**裁定**：挖出来的是一个新的瓦片 `'pit'`，语义是**一格深、有底的口袋** ——
`supportOf('pit')` 返回 `'brick'`（掉进去的人停在坑里），而 `isSolid('pit')` 仍为假
（坑口上方那一格停不住，所以走在上面的人**会掉进去**）。左右是砖、上下无梯 → 出不来，
只能等土长回来；土落下来时人还在里面就是死（**玩家与敌人同一个规则**）。

依据是归档原型 `legacy/canyon.html:92`：`hAt(x,y)` 里 `h = Math.max(1, h-1)` ——
**挖出来的坑永远不会挖穿世界**，坑底那一格留着；同文件 127-129 行的
`buriedPlayer()` / `buriedEnemy()` 正是"回填时人还在里面就死"，两个角色走同一条。

**连带结论（重要，影响玩法）**：玩家从此**也会**掉进自己挖的坑并被困住，挖完接着往前冲 =
把自己埋了。这是原版的手感（挖坑是给追兵的，不是给自己开路的），L1 的提示词已按这条改写。

**"踩其头顶跨越"已补上（2026-09-19，同一轮试玩）**：原版里守卫落坑受困之后，玩家正是踩着它的
头顶跑过去的 —— 这是挖坑这条玩法真正的收成。用户报的原话是：*"我挖了一个坑并且机器人也掉进去了，
结果立刻我往前走也判我掉进去了。"* 实现方式是给"支撑"加一条**例外**：坑里**有人**时，坑口那一格
由那个人撑着（`world/graph.ts` 的 `supportOf` ⑤，`bridges` 参数）；空坑照旧是陷阱，所以这条
不会把坑变废。`bridges` 的推导只有一个出处（`sim.bridgesOf`），移动层、渲染层摆角色高度、
HUD 方向提示三处都读它 —— 否则迟早漂成"人能站住、却被画在坑里"。

> 配套的一条：**跨折痕那一步不扣移动冷却**（`fold.isSeamStep`）。折痕两侧最内列在世界同一个位置，
> 那一步位移为 0，照常扣冷却会让角色在墙角停一整个间隔（用户："机器人经过转角的时候明显会停顿一下"）。
> "零位移零冷却"不等于加速：绕拐角与直走同样格数所花的时间一致。

### 八-5 试玩裁定（2026-09-19）：**墙角重整 —— 折痕两侧的格子必须贴在折痕之外**

用户试玩原话：*"机器人在经过两个侧面转角处的路线很奇怪，像是先走了转角，然后掉头，然后再次掉头。"*

真 bug，而且**不在动画里**。折痕两侧最内列的两格（`A: fold-1` / `B: fold`）当时**以折痕线为中心**
摆放（`halfExtent = fold - 0.5`、`toWorld` 里 u 从折痕线量起），于是那两格各有一半伸到对面去：
`A: fold-1` 整个落在 **B 面背板之后**（被 B 面挡住、看不见），`B: fold` 对称地落在 A 面之后。
玩家/无人机一走进那两格就"进了墙"——`A: fold-1 → B: fold` 的折痕一步看起来就成了
"走进墙里、再从相邻的墙里出来、然后掉头"。

**裁定**：**折痕线落在整数格上**（`halfExtent = fold - 1`），格子从折痕线**往外**排
（`toWorld` 里的 `+0.5`）。于是最内列贴在墙角上、两面的背板之前 —— 可见、可走；两面的最内列
落在**世界同一个位置**，折痕一步 = **原地转 90°**（那正是"折"该有的样子；为此加过的
"绕折痕轴转 90°"补间已删 —— 不需要了）。

顺带定下的两条都属"判据只能有一个出处"：`INK` 归 0（墙砖对齐改由"折痕线在整数格"保证，
`BRICK_N = CUBE/2` 才让折痕那一对真正重合 —— 有断言钉着）；`movement.ts` 里接头方向不再自己
重算一遍折痕算术，改用 `toWorld`（它当时就是漏网的那一处）。

**代价（已记）**：两面墙的格子整体沿墙外移一格 → 关卡在**外侧各伸长 1 格**；甲板（岛台/小道）
的位置由关卡 `deck` 数据给出、不跟着动，于是它相对"折痕—墙口"这段围区**偏 0.5 格** ——
那半格是晶格决定的（甲板砖心必须是半整数才能与墙砖贴合），不是笔误。

**已知取舍**：折痕那一对是**两个格子、两个瓦片**，但位置重合。挖其中一边时另一边不会跟着变，
表现上是"挖了却看不出来"（重合的兄弟砖盖住了坑）。留给后续裁定（挖就成对 / 加一条校验规则）。

### 八-6 试玩裁定（2026-09-19）：**键位 —— 岛台/小道的 W/S 对调，接头必须在键上连续**

用户原话：*"从左侧下角出发时按 D 是往前方走（视觉右前方）；但进到小道时按 D 变成往右走，
进入岛台以后按 W 又变成往视觉的左下方走，更加反直觉。"*

**症状的根源是几何，不是映射写错**：甲板（岛台/小道）是**水平面**，而这个相机是 45° 俯视墙角 ——
水平面上的四个轴向在屏幕上**全都投成斜的**（实测每个都是 `(±0.7, ∓0.3)`）。也就是说甲板上
不存在"按 W 就往屏幕正上方"，只能在四个斜方向里**挑分配**。

**裁定**：让**每个键落在自己那个屏幕象限里** —— 甲板的 `up`/`down` 对调（`up`→右上、`down`→左下），
于是 `d`↘ / `w`↗ / `a`↖ / `s`↙。**墙面一个键都不动**（墙面上左右 = 屏幕左右、上下 = 爬梯，
本来就是对的）。

**配套（不加就不成立）**：B 面接头的 `enterDir` 从 `up` 改成 `down` —— 进门的键必须和
"进小道之后沿着它继续走"的键**是同一个**（A 面：`d` 进、`d` 继续；B 面：`s` 进、`s` 继续）。
这条现在有测试钉着（`test/movement.test.ts`：对每个接头断言"唯一那个走向另一格甲板的方向
== `enterDir`"）—— 改键位时正是它把 B 面接头一起改掉的。

### 八-6b 同一轮试玩的两条补丁（2026-09-19）

1. **接头的"出去方向"从小道自己那侧算**。用户原话：*"沿着岛台小道从岛台方向跑去右侧墙，…
   走到最后一格，但是无法走到右侧墙面的格子上，按任何键都走不上去。"* —— 根因：以前"往外"
   是从墙面格与甲板砖的**世界坐标差**取主导轴，而 B 面接头上 `dx` 与 `dz` 正好是 ±0.5 的
   **平手**，靠 `>=` 的先后破给了 x ⇒ "沿小道按 `w` 过来、到尽头却必须按 `d` 才上得去"。
   现在 `stepOnDeck` 用 `jettyOutward`：接头那格在甲板上的邻居只有一个，它的反向就是"往外" ——
   **甲板数据是唯一出处**，世界坐标只在不规则形状时兜底。测试把**两侧**都钉住
   （进门的键 == `enterDir`；沿小道走来的键 == 能上墙的那个）。
2. **跨接头的那一步会掐掉"按住不放"**。用户原话：*"按着 a 键会在到达墙面时自动转换方向，
   这是不对的。"* 判据是**世界方向**：门（甲板 ↔ 墙面）两侧的键含义不同，按住不放会被带着
   拐进另一条走廊 ⇒ 掐掉（要重新按键）；而**折痕**是同一条走廊折了一下（`stepDelta` 两侧
   给出同一个世界方向）⇒ 不掐，"沿走廊一直走就能过去"那条教学照旧成立。
   实现：`input.holdBroken` / `Input.breakHold`，`main.ts` 在 `entered` 事件里按
   `metrics.sameWorldDirection` 判定。

### 八-7 试玩裁定（2026-09-19）：**给角色一个朝向指示（问题不止在键位）**

用户原话：*"我觉得还有一点造成现在的困境的，是当前玩家角色是个方块，看不出前进方向……
或者在方块正下方画一个箭头，指示当前的面对方向。"* —— 他说得对，而且这一条**还欠着一条旧账**：
§八-4 早就裁定"折痕处角色朝向跟随转 90°"，但角色是个**正方体**，转了也看不出来。

**裁定**：在角色（含无人机）**脚下的地面上**画一个扁平三角箭头，指向"当前朝向对应的世界方向"。
朝向的世界方向由 `metrics.stepDelta` 给 —— 与 HUD 那条"屏幕方向"提示**同一个函数**
（所以"提示说右、箭头却指别处"不可能发生）。跨折痕那一步在这里自动变成"转过弯之后"的方向，
于是过折痕时的 90° 转身第一次变成**看得见的事实**。

### 八-8 实现裁定（T15）：**攀爬者的身份 = "可爬崖" = 它能上岛台**

计划里 T15 的验收是"可爬崖 / 跨折痕追击、双态巡逻/追击、速度 ≤90%、落水行为同 §八-2"。
落到本作的模型上，**"可爬崖"就是 `STALKER_STEP = { decks: true }`** —— 它能走甲板
（岛台/小道），而无人机被用户裁定"只在墙面内"。于是两者真正的分工是：

| | 无人机 | 攀爬者 |
|---|---|---|
| 能不能上岛台 | 不能（岛台是安全区） | **能** —— 安全区取消 |
| 速度 | `DRONE_MOVE_TICKS = 24`（1/3 速，"一直在来"） | `STALKER_MOVE_TICKS = 20`（玩家的 40%，"快一点、但一样追不上"） |
| 其余 | 两段式 / 寻路 / 落坑受困 / 延时重生 —— **同一套引擎**（`ai/drone.ts`） | 同左，只在 `ai/stalker.ts` 里声明能力与速度 |

**顺带修掉一个只有它才会暴露的真 bug**：追击取"路径的第一步"原先是按摊平网格的坐标差算的，
那只认识墙上的邻居 —— 而**接头那条边**（墙面 ↔ 岛台/小道）既不同行也不同列，于是追到接头
就返回 `null`。无人机一直没暴露它（它的图里没有甲板节点），攀爬者第一步就是接头。现在
`firstDir` 分两支：两端都在墙面走坐标差（**踩空也是合法一步**，追兵会走进坑口 —— T12-e），
一端在甲板上则问 `step`（那条边的方向是接头声明的）。

> 调色板上新加的 `PALETTE.stalker`（深青）不是随手挑的：它必须落在探针 6 条色相规则的**缝隙**里
> （见 `palette.ts` 里那张逐条对照表）。这份"调色板 × 探针"的契约以前只有注释在维护 ——
> 现在有 `test/palette.test.ts` 拿三种实体的颜色逐条过一遍，断言"只命中自己那一条"。

### 八-9 实现记录（T16）：**L2「织网」** —— 双岛、岛间小道、跨折痕横杆、攀爬者登场

计划 T16 的三件事都落地了（`core/level/levels/l2.ts`）：

1. **双岛 + 岛间小道**：宝物分在两张岛上，第二张岛**只能**经一条 1 宽的岛间小道过去
   （测试里把那条小道拿掉，第二颗宝物当场够不着 —— 咽喉成立）。水面从 L1 的"一个目的地"
   变成一张网。
2. **跨折痕横杆**：`r3` 的 `col 13/14` 是杆，吊着可以直接跨过折痕；杆下面那两层特意挖空。
   这条顺带**补齐了设计文档 §四 规则⑦的校验**（"连杆下方非实心"）—— 它此前从未实现过
   （L1 里没有杆，所以一直没人发现），现在 `validate` 会报 `barHangable`。
3. **攀爬者登场**（T15）：一个 `stalker`，位置在 B 面最远端。

**墙面骨架刻意沿用 L1**（梯子列、落水缺口、出口/闸门一字未动）：L2 要教的是水面上的新走法，
不是重新教一遍爬梯子。**代价**是两张关卡的墙看起来很像 —— 由 T17（L3：柱 + 长连杆 + 多折痕）
和 T18（规模）去拉开差异。

**两处真 bug 是探针抓出来的**（都是"规则过期、而此前没有关卡能触发它"）：

- `bar` 的色相规则还停在**深色版**的品红上，而横杆早就改成陶土红 —— L1 没有横杆，
  `EXPECTED_FEATURES` 只在"关卡真的声明了横杆"时才断言，于是这条**坏了整整一版**；
- `cyan`（芯片）的旧门槛能把**水面**也算成"亮青"，`prize` 的门槛能把**陶土红横杆**算成"宝物"。

于是把"调色板 × 探针"的契约从"三个实体"扩到**全表**：`test/palette.test.ts` 现在逐项断言
"要么只命中自己那条、要么一条都不命中"，新加颜色时漏登记也会被 `Object.keys` 那条比对挡住。

### 八-10 试玩反馈（2026-09-19，L2）：**三种"规则对、画面没跟上"**

用户在 L2 上提了两条，背后是**三个同类的渲染层缺口** —— 规则层一直是对的，错的是"画面没有
跟着 state 变"：

1. **宝物只画了第一颗**：`islandAndJetties` 取的是 `level.treasures[0]`。L1 只有一颗所以从没
   暴露；L2 有两颗，于是第一颗根本没画出来。
2. **收走的宝物不消失**：宝物（以及 props 里的芯片）建一次就不动。于是"取了宝物没有任何反应"，
   而红色闸门要**两颗**才开 —— 玩家的感受就是"我明明取了，什么也没发生"。
3. **闸门开了，梯子看不见**：闸门开启是 `硬砖 → 梯子` 的**tile 变化**，而梯子的 mesh 是一次性
   建的 —— 路通了，那一格却什么都没有（T13 的"通天梯"只有规则、没有画面）。
4. 顺带一条**建模后果**：折痕两侧最内列在世界**同一个位置**，而横杆/梯子这类**有方向**的件
   在那儿会画成一对交叉（用户："看到交接处有个粉红色的交叉，不知道有什么意思？"）——
   现在同一对里只画靠 A 面那一根（对称的芯片/出口**不去重**：它们各自都算数）。

**修法（一条共同的纪律）**：渲染层不推演规则，只把 state 的事实画出来 ——
`Stage` 新增 `setTreasures(remaining)`（与既有的 `setGrid` 同构），道具层改成**按网格重建**
（判据是"道具签名"，挖坑不会触发），并在 `main.ts` 启动时**把 state 推给 stage**
（`createStage(level)` 只能读关卡原始数据，而"开局状态"未必与关卡文件相同 —— 这一条是
上面 2/3 两处共同的根因）。回归在 `test/props.test.ts`（纯数据，不需要 WebGL）。

### 八-11 试玩裁定（2026-09-19，L2）：**连杆是墙面平面内的东西，不该挂在折痕上**

用户原话：*"你的连杆在两面墙交界处，不知道什么意思。这个位置不应该有连杆。我想象的是连杆应该
位于左右面，或者从一个高处走到中间岛台上的高塔，塔有梯子可以上下；或者有多个断开的岛台可以
通过连杆到达。"*

**他是对的，而且这是我照计划书照抄出来的错**：计划书 T16 写的是"跨折痕横杆"，我就把它摆在
`col 13/14`（两面墙的交界）—— 但连杆是**墙面平面内**的物件（原版语义），交界处是"两片墙会合
的棱"，在那个位置摆一根杆没有意义，玩家看到的只是两根杆交叉成的一个 X。

**裁定**：

1. **连杆回到墙面**，并且用它本来的用途 —— 跨**落水缺口**：L2 的两个缺口（`r0` 的 `col 5/22`）
   正上方各挂一根杆（`r1`）。踩上缺口不再是"必掉"，而是**吊着跨过去**；吊着按 `s` 松手仍会
   掉进水里 —— 危险还在，但从"必死"变成"要小心"。这一版先落这条。
2. **另外两条留给 T17 / v2+**（用户同一次提的，都对，但都需要新机制）：
   - **岛台高塔（塔上有梯子上下）**：需要甲板有**高度**（现在的甲板是一层平板，`DECK_TOP_Y`）；
   - **断开的岛台之间用连杆连**：需要"甲板上的连杆"（吊在杆下横渡水面）—— 甲板目前只能当砖面。
   两条都要求先给"甲板"这个概念加一维（高度 / 可吊格），而计划书 T17 的"柱 + 长连杆"、
   v2+ 的"岛上高柱、柱间长连杆"正是它们的位置。

> 顺带一条纪律：这次是**照抄计划书而没有回问"这在本作的模型里是什么"**造成的。计划书是
> 2026-09-13 写的、在 L2 存在之前；凡是它给出的**具体摆位**，落地时都要按当时的模型复核一遍。

### 八-12 试玩裁定（2026-09-19）：**甲板加一维 + `Z`/`X` 是世界上下**

用户原话：*"我在想的是 `awsd` 只控制方向，`Z`/`X` 控制上下……总之 `awsd` 只控制方向，不会转意。"*

**这条点中了折面几何的根本矛盾**：两种地形需要的键数不一样 —— 墙面（竖直）要"左右 2 个 +
爬 2 个"，甲板（水平）要"前后左右 4 个"。4 个键同时表达两种面，就**必然有一处转意**
（`w`/`s` 在墙上=爬、在甲板上=前后）。换哪四个键都一样，只是把矛盾挪个地方。

**裁定**（三组动作，各管各的）：

| 输入 | 含义 | 墙上 | 甲板上 |
|---|---|---|---|
| `WASD` | **面内**四方向 | 只有 `a`/`d` 沿墙左右 | 前后左右 |
| `Z`/`X` | **世界上下**（`Lift`） | 爬梯 / 下梯（吊杆时 `X` = 松手） | **换一层**（塔的梯子） |
| `Q`/`E` | 挖（`Dir` 的左右） | 左挖 / 右挖 | 没有可挖的砖 |

**墙面上的 `w`/`s` 干脆不做事**（用户 2026-09-19 追加："禁止 ws 可以上下爬梯子"）。原来的
"`Z`/`X` 与 `w`/`s` 在墙上等价"被否掉了 —— 冗余看着无害，实则**留下了两个答案**：
"我要上去"在墙上可以是 `w` 也可以是 `Z`，而到了甲板上就只剩 `Z`。**只有一个答案**才叫不转意。
顺带一个必然后果：吊在杆上"松手"从 `s` 变成 `X`（`X` 本来就是"往下"）。

判据落在 `app/input.ts` 的 `moveAllowed(dir, surface)`：**`WASD` 在墙面上只有左右两种走法**。
它与 `movement.step` **不重复** —— `step` 管"这个走法合不合法"（AI、脚本、回放在用），
`moveAllowed` 管"**哪个键**代表它"。`core/types.ts` 的 `surfaceOf(cell)` 是"我在哪种面上"的
唯一出处（输入层与方向提示都从它取）。

不用方向键的 `↑`/`↓` 做升降：方向键是 `WASD` 的**别名**（两套都能用），若 `↑` 是升降而 `w`
是"往北"，两套输入就分裂了。

**甲板因此多了一维**（`Cell.level` / `DeckCell.level`，只有面 `'I'` 有意义）：

- 同一 `(x, z)` 上可以叠好几层；层编进 `cellKey`（`I:5,3@1`），于是"同一格的上下两层"是
  **两个不同的节点** —— 图、可达性、存档都不用为塔写特例；
- **上下怎么连**：同一 `(x, z)` 的相邻两层都是甲板 → `Z`/`X` 就能走（`stepLift`）。
  这个判据是**唯一出处**：渲染层照它画"梯子标记"（`scene.ts` 的 `islandAndJetties`），
  梯子不给任何额外能力，画错也不会"看得见走不到"；
- `level = 0` 是水面上的那一层，**所有既有关卡数据一字不改** —— `cellKey`/`parseCell`
  对层 0 省略 `@` 后缀，旧键逐字节不变；
- 宝物也带层（塔顶那颗 `{x, z, level: 1}`）—— 采集判定必须一起比层，否则站在塔底就会把
  塔顶那颗取走。

**第一件用它的东西**：L2 的 B 岛上叠了 2×2 一层，第二颗宝物放在**塔顶**（必须按 `Z` 上去）。
柱、长连杆、多折痕穿越（T17）从此有了落脚点。

### 八-13 接头**不许抢走廊**（2026-09-19，用户实测之后）

用户报："沿走廊一直按 `d`，走到中间某一格，人却拐进水里那条小道了。" 这不是显示问题，
实测出来是**两件**事：

| 位置 | 按 `d` 的世界位移 | 屏幕 |
|---|---|---|
| 出生点 `A:0,1`（沿墙） | `(0,0,-1)` | `→↑` |
| 接头 `A:7,1`（上小道） | `(+1,0,0)` | `→↓` |

①差 90°（小道是沿墙的**法线**出去的，不在墙的砖格里 —— 墙的砖格只有"沿墙 / 上下"两条轴）；
②**更要紧的是那一格再也到不了 `col 8`** —— 走廊被接头切断了。

**根因**：接头被排在网格**之前**（当年的理由是"不这样就是单向门，小道下得去上不来"）。
那个理由对"上不上得去"成立，代价却没人算过：**接头吃掉一条走廊走法**。

**改法**（两层）：

1. `movement.step` 现在**先问网格**（`gridStep`），网格走不通才问接头（`jointStep`）。
   于是"抢走廊"**在结构上不可能发生**。
2. 配套一条校验规则 **⑧ `jointNeverEntered`**：接头的 `enterDir` 必须是那一格**本来就堵住**
   的方向，否则它永远进不去（而且还在吃那条走法）。判据直接调 `gridStep` —— 与 `step` 内部
   同一个函数，**不在这里重写"这一步能不能走"**。

数据上要改的只有 A 面那两处：`A:7,1` 从 `right` 改成 **`down`**（`B:20,1` 本来就是 `down`，
它一直是对的 —— 那一格脚下是砖不是梯，所以往下堵死，谁都不抢）。

**顺带废掉一条老性质**："进门的键 = 沿小道继续的键"。要满足它就必然让接头用上一个**走得通**
的方向 —— 那正是这个 bug。现在接头是 `X`（世界向下：那一格往下堵死，所以 `X` 就是"出墙"），
而从小道那侧上墙照旧用沿小道那个键（`stepOnDeck` 的 `outward`，与 `enterDir` 无关）。
`movement.test.ts` 里那条测试换成了新的两条性质：**小道那侧仍能上墙** + **墙面那侧不抢**。

### 八-14 键位的最终形态（2026-09-19 定稿）

| 输入 | 墙面（竖直面） | 甲板（水平面） |
|---|---|---|
| **`WASD`** | `w`/`s` = **上下**（竖直轴，爬梯）；`a`/`d` = **沿走廊左右**（横向轴） | `w`↖ / `s`↘ = **屏幕纵深主轴**；`a`↙ / `d`↗ = **屏幕横向次轴** |
| **`Z`/`X`** | — 什么都不做 | 上一层 / 下一层（塔） |
| **`Q`/`E`** | 后下方挖 / 前下方挖（相对**朝向**） | （甲板没有可挖的砖） |
| **`R`** | 重开本局 | 同左 |

**墙面为什么是 `a/d` + `w/s`**：场景是**一张平面折了 90°**，而相机方位恰好 45° —— 两者同构。
后果是摊平网格上的同一组方向在两面墙上投到屏幕上**是同一个方向**（`col±1` 都水平、`row±1` 都竖直）。
所以 `a`/`d` 天然就是"沿走廊前进/后退"，按住 `d` 能一路绕过墙角 —— **折痕对输入是透明的**。
（有测试钉着：`test/input.test.ts` 拿真实相机矩阵的右轴/上轴验。）

**甲板为什么是经典等轴测（菱形）映射**（用户 2026-09-19 定稿）：水平面的两个轴在这个相机下都投成
(±0.7, ∓0.3)，四个方向落成四个斜向。取 `w`↖ `s`↘ 为**主纵深轴**、`a`↙ `d`↗ 为**次横向轴**，
于是**两面在空间认知上对称**：`w`/`s` 管一条轴、`a`/`d` 管另一条，没有哪个键在某个面上被"抠掉"。
左手也顺：中指在 `w`/`s` 上走一条轴，食指/无名指在 `d`/`a` 上走另一条轴。

**丁字路口（用户方案 A，2026-09-19 定稿）**：立面上遇到"走廊 ↔ 水面小道"的接口那一格时，
**`a`/`d` 照旧沿墙走（路口不抢它们）**，**`s`（向下 / 朝屏幕前方）拐上小道**。用户在 45° 视角下
看到小道是"朝下前方伸出来的"，手指本能就是按 `s` —— 不用看说明书。

这不是特判，是**规则的自然结果**：接口声明的方向就是 `down`（`LevelDef.joints`），
而那一格"往下"本来堵死（脚下是实心砖、不是梯子），所以 `s` 在那里没有别的意思。
校验规则⑧（`jointNeverEntered`）保证这条前提对每张关卡都成立。
**从小道走回墙上照旧**：走到尽头就上去了（甲板那侧的方向由小道自己的数据算，与接口数据无关），
所以不需要"撞墙再按 A/D 吸附"那种确认机制。

**挖：机制是"斜下方"，命名讲清**（用户 2026-09-19）。`Q`/`E` 取的是"朝向那一侧、**斜下方**"那一格
（原版 Lode Runner 语义 —— 在脚边挖坑让人掉进去，而不是挖面前那堵墙），**相对朝向**所以折面两侧都成立。
命名一度叫"前挖/后挖"，容易被读成"推土机挖面前的墙"，所以提示里写的是 **`Q` 后下方 / `E` 前下方**。

**爬梯不改朝向**，理由有两条：①`Q`/`E` 是相对朝向的，朝向被刷成 `up` 会让"前下方"变成"往上挖"（非法）；
②朝向记号是贴地的，朝上时它在屏幕上的投影长度为 0，直接消失。

**朝向的可见性（2026-09-19）**：身体**正面**贴两个高亮小方块（"护目镜"，用自己的小 group 跟朝向一起转，
而身体保持网格对齐），贴地三角作为"与网格对齐的基准"同时保留 —— 45° 俯视下光靠贴地记号，
在移动中或被砖挡住时很容易被漏看。跨折痕的"原地转 90°"用 **0.08s 的角度补间**（`aimAngle`）平滑掉，
读起来是利落的贴墙拐弯而不是卡顿。

**输入层的形状跟着变了**：`KeyState` 存的是**键名**而不是方向 —— 键 → 方向现在是**按面分**的，
存方向就等于在按下那一刻把它钉死，跨过一条折痕就是错的。`moveIntent(state, surface)` 每 tick 解释，
"在这个面上没有对应键"的锁存**作废**而不是欠着。`surface` 由 `main.ts` 以回调给出
（`surfaceOf(player.cell)`），于是"按下"与"采样"不可能各算一套。

### 八-15 T17：柱、长连杆、甲板上的连杆（L3「立柱」）

**甲板多了一种格**：`DeckCell.hang`（省略 = 板）。它不是板、是**横杆** —— 与墙上 `TileKind.bar`
逐字同构：`supportOf` 返回 `'bar'` → 停驻方式是 `hang`；板 ↔ 吊 ↔ 板 都能走；**吊着往空中挪要被拦住**，
因为"松手"必须是一个**决定**而不是一次失误。

**松手 = `X`**，而且这不是新键：甲板上 `X` 本来就是"往下" —— 站在板上是**下一层**，
吊在杆上是**松手**。同一个键、同一个词、两种处境。

**从杆上掉下来**是 `fallTo` 的自然推广：墙上它是"沿着行往下找支撑"，甲板上是"同一个 `(x, z)`
往下找层"。**由同一个函数回答** —— 两者是同一个问题的两套坐标系，分成两份实现必然漂开。

`deckKey` **不含 `hang`**：键标识"哪一格"，而"是板还是杆"是那一格的属性 —— 于是旧关卡数据一字不变。

**L3「立柱」**（`src/core/level/levels/l3.ts`）把这三件东西摆在一起：两处**三格宽**的落水缺口
（正上方是三格长的连杆）、两座岛之间**只有一根杆**（吊着荡过去）、B 岛上一座**三层高的柱**
（宝物在柱顶，连按两次 `Z`）。梯子换到了 `3/11/16/24`（L1/L2 是 `3/10/17/24`）——
**换一关换一副骨架**，否则 L3 只是 L2 的换皮；缺口的两条硬约束（不是梯子列、两侧邻格可达）照旧守着。

### A.1 一句话定位（未变）

把《淘金者》(1983) 的"挖地困敌、收集逃生、高低差走位"从 2D 升维到 3D，**保留严丝合缝的格子策略判定**。
核心追问始终是：**哪些谜题只有 3D 里才存在？**

### A.2 前人为什么失败（本作要避开的坑）

| 作品 | 做法 | 遗留问题 | 本作对策 |
|---|---|---|---|
| Lode Runner 3-D (N64, 1999) | 关卡 3D 化，角色沿轨道走 | **镜头遮挡**被广泛批评 | 固定正交视角正对墙角 + 两面都是 1 砖厚浮雕 → 无自遮挡（§1.3-2） |
| Cubic Lode Runner (PS2, 2003) | 立方体关卡 + 整关旋转 | **4 向逃跑稀释了追逃张力** | 折面 + 水沟构成隘口（岛台是唯一通路），张力集中在过桥与挖坑（§1.3-5） |
| 本作 | 原版关卡沿中线折 90° | — | 3D 不是视角噱头，而是**机制**（折痕 + 水沟） |

### A.3 仍然有效的设计支柱

1. **固定 45° 轴测、正对墙角棱线**（原案已有；现在是唯一视角，不是可选项）
2. **跨面无缝移动**：进入另一面时输入方向按本地坐标系重映射 —— 即 v2.0 的**折痕边**规则（§1.5-1）
3. **体素挖地**：可破坏 → 凹坑 → 延时自动重组 —— 即**原版挖/回填/活埋**语义（无需自创规则）
4. **规则忠实原版**：无跳跃、守卫也会用杆、杆下/梯井不可挖（护绳）、挖→坠→被埋→以身填坑
5. **逻辑与渲染解耦**：状态是纯 tile 数据，函数不碰 Three.js → 可无头测试（这正是原型跑出 25 项回归的原因，v2.0 继承为 §三 红线）

### A.4 敌人名单（原案 3 种 → v1 做 2 种）

| 敌人 | 原案设定 | v2.0 处置 |
|---|---|---|
| 巡逻无人机 Patrolling Drone | 沿平面匀速巡逻；落坑受困；玩家可踩其头顶跨越 | **保留**（= 原版守卫行为） |
| 潜伏攀爬者 The Stalker | 无视重力，可在任意竖直面爬行包抄 | **保留但重定义**：两面都已是竖直面，"无视重力"不再构成特色 → 改为**可跨折痕追击**（高威胁度来源） |
| 地形重构者 The Reconstructor | 加速填坑 + 救援被困同伴 | **v1 砍掉**（抬高 AI 复杂度、收益不明确，见 §七） |

### A.5 关卡难度递进骨架（保留；关卡内容按 v2.0 重写）

1. **L1 教学**：收集 → **首次跨折痕** → 挖坑困敌 → 到达出口（原案"觉醒之角"的骨架）
2. **L2 引入高威胁**：加入可跨折痕追击的攀爬者（原案"测地织网"的骨架）
3. **L3 组合考试**：多折痕穿越 + 柱/长连杆 + 多岛台（原案"移位棱柱"的**位置**，但机制换成 v2.0 的连杆/多岛，不再是重力翻转）

### A.6 美术基调（保留）

精致机械工程学（Precision Mechanical）：哑光金属 + 发光电路 + 微型体素方块；数据芯片发冷光、坑洞边缘流光栅格、多向墙面投长阴影。（v10 mock 的配色即此方向）

### A.7 原案中已作废的部分（防误读）

三面内角（含底面）、"外密内疏"防遮挡法则、几何空间旋转（90° 重力翻转）、X 光透视遮挡处理、8³/10³/12³ 体素网格规格 —— **全部作废**，理由见 §1.4。
